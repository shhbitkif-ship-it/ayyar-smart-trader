# مدل اجرایی تیم چندعاملی عیار هوشمند

## هدف
تقسیم توسعه عیار هوشمند میان عامل‌های تخصصی هوش مصنوعی، با یکپارچه‌سازی کنترل‌شده و نظارت معماری مرکزی. این سند به‌تنهایی به معنی فعال بودن عامل‌های خارجی نیست؛ اجرای هر عامل نیازمند اتصال مدل/سرویس و مجوزهای لازم است.

## نقش‌ها
1. **مدیر پروژه و معمار مرکزی (Orchestrator):** مالک نقشه راه، مرزبندی وظایف، قراردادهای بین بخش‌ها، اولویت‌بندی، بازبینی تغییرات و تصمیم نهایی ادغام.
2. **عامل کیفیت داده و بازار:** منبع قیمت و کندل، timestamp semantics، freshness، session calendar، gap classification، provenance و fallback.
3. **عامل موتور تحلیل:** شاخص‌ها، رژیم بازار، چندتایم‌فریم، سیگنال و قواعد NO_TRADE؛ بدون فعال‌کردن اجرای واقعی.
4. **عامل بک‌تست و پژوهش کمی:** هزینه معامله، جلوگیری از look-ahead، out-of-sample، walk-forward، robustness و گزارش محدودیت‌ها.
5. **عامل Android/UI:** ناوبری تب‌محور، داشبورد، وضعیت داده، دسترس‌پذیری و نمایش شفاف LIVE در برابر آمادگی تحلیل.
6. **عامل Backend/API:** قراردادهای API، امنیت، پایداری، cache، storage و observability.
7. **عامل QA و امنیت:** تست واحد/یکپارچه، regression، بررسی اسرار، وابستگی‌ها و release gates.

## قواعد همکاری
- هر عامل فقط محدوده فایل/ماژول تعیین‌شده را تغییر می‌دهد.
- کارها در branch مستقل انجام و از طریق Pull Request ارائه می‌شوند؛ نوشتن مستقیم روی main ممنوع است.
- عامل باید پیش از تغییر، قراردادها و تست‌های موجود را بخواند و از تغییرات نامرتبط خودداری کند.
- خروجی هر کار شامل: هدف، فایل‌های تغییرکرده، فرض‌ها، ریسک‌ها، تست‌های اجراشده و نتیجه باشد.
- هیچ عامل حق ندارد تست ناموفق را پنهان کند، داده گمشده را جعل/پر کند یا نتیجه بک‌تست را تضمین سود معرفی کند.
- تغییرات داده، موتور، ریسک و معاملات نیازمند بازبینی مستقل هستند.
- ادغام فقط پس از CI سبز و بازبینی معماری انجام می‌شود.

## مرز ایمنی مالی
- اجرای سفارش واقعی غیرفعال باقی می‌ماند مگر آنکه کاربر جداگانه و صریحاً تصمیم دیگری بگیرد و کنترل‌های لازم طراحی و تأیید شوند.
- داده stale، ناقص، نامعتبر یا دارای شکاف تأییدنشده باید fail-closed شود: NO_TRADE / UNAVAILABLE.
- هیچ داده ساختگی، کندل مصنوعی یا fill پنهان برای عبور از کنترل کیفیت مجاز نیست.
- نتایج پژوهشی/بک‌تست باید همراه هزینه‌ها، اندازه نمونه، محدودیت‌ها و تفکیک train/test نمایش داده شوند.

## قرارداد تحویل عامل
هر تحویل باید شامل موارد زیر باشد:
- مسئله و معیار پذیرش
- محدوده فایل‌های مجاز
- تغییرات و دلیل فنی
- تست‌های اجراشده و خروجی واقعی
- ریسک‌های باقیمانده و کار بعدی
- عدم تغییر رفتار خارج از محدوده

## ترتیب اولویت فعلی
1. کیفیت داده و تعریف صحیح شکاف‌های بازار در برابر شکاف‌های غیرمنتظره
2. موتور تحلیل و ایمنی سیگنال
3. بک‌تست و walk-forward معتبر
4. رابط کاربری تب‌محور و نمایش صریح سلامت داده
5. سخت‌سازی API، امنیت و انتشار

## اتصال مدل‌های خارجی
برای استفاده واقعی از چند ارائه‌دهنده، باید سرویس‌های مجاز، API keyهای امن در GitHub Actions/Cloudflare Secrets و سیاست هزینه/سهمیه تعیین شوند. کلیدها هرگز در کد، issue، log یا اپ اندروید قرار نمی‌گیرند. تا قبل از اتصال، این نقش‌ها «تعریف‌شده» هستند، نه عامل‌های فعال.
